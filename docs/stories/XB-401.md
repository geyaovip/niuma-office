# XB-401：渠道契约、设备身份与扫码会话

- 状态：`done`
- 主文档：`docs/architecture/technical-baseline.md` 第 8 节
- 关联决策：`D-011`、`D-012`、`D-015`

## 目标

建立飞书与 Telegram 共用的安全渠道边界，让后续私聊、群聊、离线队列和 Mac 投递使用同一组稳定 Contract，不在各渠道里重复实现身份与幂等逻辑。

## 范围

- 必须实现：设备安装身份、本机私钥保护、设备签名请求和服务端公钥登记 Contract。
- 必须实现：Channel Adapter、PairingSession、ChannelBinding、ChannelEnvelope、DeliveryReceipt 与幂等键 Contract。
- 必须实现：5 分钟、一次性、可取消/刷新/消费的 Pairing Session 状态机；二维码只包含短时令牌或官方授权入口。
- 必须实现：签名验证、时间窗口、防重放、来源身份和同一 `provider_event_id` 幂等逻辑的服务层基线。
- 本 Story 不修改真实飞书/Telegram 第三方配置，不开发具体 Bot 交互，不接入登录。

## 验收

- Contract 能表达等待扫码、已扫码待确认、已绑定、已过期、已取消、身份冲突和权限撤销。
- 过期、重放、二次消费、签名不符和事件重复均有自动化测试。
- 客户端、云端和后续两个渠道不依赖临时字段或特定 provider 的内部数据结构。
- 真实密钥、Bot Token、App Secret、服务器地址和个人数据不进入仓库、日志或测试快照。

## 验证命令

- `npm run check`
- `npm run test:desktop`
- 新增渠道 Contract 与状态机定向测试

## 完成记录

- `@niuma/contracts` 新增 Channel、PairingSession、ChannelBinding、ChannelEnvelope、DeliveryReceipt 和 SignedDeviceRequest 的严格 Schema。
- 新增独立 `@niuma/channel-adapter`，实现 5 分钟一次性会话、状态迁移、Token 哈希与常量时间比较、Ed25519 设备签名验证、5 分钟防重放窗口和 provider event 幂等基线。
- macOS 首次启动生成稳定的 `device_installation_id` 和 Ed25519 密钥对，公钥可登记，私钥经 macOS Keychain 能力加密后落盘，Renderer 无法读取。
- 测试覆盖过期、二次消费、错误 Token、连续失败、签名不符、时间窗口、Nonce 重放和 provider event 重复；渠道包 5 项、桌面端 67 项测试通过。
- 未签名 macOS 应用重新打包并实际启动，设备身份生成与安全存储路径通过。
